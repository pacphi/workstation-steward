## Why four areas

A machine has several software supply chains, and they drift in different ways: a toolchain falls behind, an app
bundles an old runtime, an AI tool updates itself, a project pins a path that a prune removes. Left to one script,
they overlap without knowing about each other: a general upgrade can reinstall a tool with install scripts its own
qualification had blocked. Giving each supply chain its own area, policy file and commands makes the drift visible
and the rules enforceable (D1).

## The four areas

| Area | Owns | Policy (in the instance) | Commands |
| --- | --- | --- | --- |
| **Supply chain** | mise tools, npm -g hybrids, Homebrew, apps, App Store, macOS, trust stores, Docker, IOCs, and mise itself. AI command-line clients count as ordinary tools here | `mise/`, `supply-chain/host.toml`, `supply-chain/hybrids.toml` | `steward sc …` |
| **AI tooling** (add-on) | Ruflo and AgentDB, AQE (a shared, patched runtime and CLI), RuvNet Brain, RuVector, the shared launchers, the guards (auto-update off, daemon autoStart off, hook shims), and each project's AI launchers | `ai-tooling/ai-tooling.toml` | `steward ai …` |
| **Projects** (add-on) | Discovering every project under `[projects] roots`, the registry of decisions, per-project onboarding that calls the other areas | `projects/registry.toml` | `steward projects …` |
| **Fleet** | The GitHub side: Renovate config, PR consolidation, required checks, local checkouts after merges | each repo's `renovate.json` | `steward fleet …`, `skills/pr-consolidation/` (its `rules.md`) |

## How the areas meet

- **Supply chain decides *when*, AI tooling decides *whether*.** A version may come in only once it is 3 days
  old, or is the first patched release for an advisory. AI tooling never installs a version supply chain
  hasn't cleared, and adds its own qualification on top.
- **AI packages stay where they install (D2).** mise or npm -g installs them, but `ai-tooling.toml` lists them
  as AI-owned. `steward sc upgrade` skips them, and Renovate opens their PRs only on dashboard approval.
- **Node patches carry AI state safely.** `steward sc node-patch` reinstalls the hybrids; for Ruflo, that path backs
  up every policy folder before a version change and installs only the qualified scripts.
- **Projects run the per-project steps of both areas.** Each project chooses its own AI tools, or none.

## Engine and instance

The engine (this repo) holds no one's data. Everything about a machine lives in the **instance** (D39): a folder
holding `steward.toml` and the policy files, at the same relative paths as here — `mise/`, `renovate.json`,
`supply-chain/{host,hybrids}.toml`, `supply-chain/verify.tsv`, `supply-chain/vendor/`, `ai-tooling/ai-tooling.toml`
and `projects/registry.toml`. [`examples/`](../examples/README.md) is a complete one. The engine finds it at
`$STEWARD_INSTANCE`, else in its own folder when that holds a `steward.toml`, else in `~/.config/workstation-steward`.
Keep yours in a private Git repo: it names your projects.

**`steward.toml` (D10)** says where things are; the area files say what's allowed.

- **What it holds:**
  - `schema`: the file's format (D40);
  - `[projects]`: roots, excluded paths, depth, extra skip folders and markers, and the worktree rule (D15);
  - `[paths]`: state and cache (both default to XDG), the mise config folder, and where the tools keep installs
    and settings: `mise_data_dir`, `ai_tooling_root`, `claude_dir`, `claude_json`, `codex_home`,
    `ruflo_config_dir` (mise, Claude Code and Codex defaults follow `MISE_DATA_DIR`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`);
  - `[policy]`: `min_release_age_days`, `soak_days` and `review_days`, the policies every area shares;
  - `[profiles]`: the optional areas, `ai_tooling` and `projects`, both off unless turned on. An area that is off
    refuses its commands with the reason, and `steward review` and the notices skip it;
  - `[launchers]`: extra folders searched for launcher configs;
  - `[ioc]`: extra sweep roots.
- **How it's read:** `lib/config.js` overlays the file on built-in defaults (`$STEWARD_CONFIG` points at another
  settings file; the policy files still come from the instance). Node reads instance files through `C.policy()` and
  `C.instance()`; bash through `INSTANCE_ROOT` and `SC_INSTANCE` in `lib/lib.sh`. `steward config` shows every
  effective value and where it came from; `just lint` fails on unknown keys, wrong types or unknown sections.
- **Paths in `ai-tooling.toml`** are `{{NAME}}` placeholders for the roots above (`{{AI_TOOLING_ROOT}}/aqe`,
  `{{CLAUDE_DIR}}/settings.json`); `C.policy()` fills them and fails on an unknown name.
- **The release-age gate** (`[policy] min_release_age_days`, default 3) applies to every area. mise and Renovate
  can't read `steward.toml`, so they keep copies: `steward sc release-age <days>` sets all three, and `steward sc
  audit` flags any disagreement.
- **The soak** (`[policy] soak_days`, default 3; D20): after anything changes what runs, the old installs stay that
  long, so going back is a link away instead of a reinstall. A soak starts at the newest receipt (a tool upgrade, a
  Node patch, a hybrid install, a repin, an onboarding, the AQE hook transport, mise itself); offboarding, the
  guards and `init` don't start one. `steward sc prune` refuses while one runs, and `steward sc soak` shows it.

## Projects: detection and onboarding

- **What counts as a project (D4):** any Git root under the roots (primaries, linked worktrees, nested repos),
  and non-Git folders with project markers (`package.json`, `pom.xml`, `Cargo.toml`, `go.mod`, `pyproject.toml`,
  `AGENTS.md`, `.claude/`, `.mcp.json` …) that aren't inside another project. The scan skips dependency, build and
  cache folders and `[projects] exclude`.
- **When detection runs:** on demand only, never in the background. `steward` with no command prints a notice
  such as "2 new projects"; `steward projects scan` lists them.
- **The registry (D5):** `projects/registry.toml` in the instance. Each entry records the path, kind, remote,
  decision (onboarded, ignored, or deferred until a date) and the AI tools chosen. Backups and receipts go to the
  state folder, never a repo.
- **Per-project tool choice:** not every project has Ruflo, AQE or Brain, and none has to. New projects default to
  none; onboarding asks tool by tool with the evidence; drift checks only the tools a project chose and reports,
  never removes, the others.
- **What onboarding gives a project (D16, D18, D21–D26):** the per-tool profiles in
  [`../projects/profiles/`](../projects/profiles/README.md), filled in per project and merged by adding only, with
  the keep-off list winning. `steward projects facets` shows what each project adapts to (stack, monorepo, Node,
  each file's Git state); `steward projects profile-check` compares every project with its profiles and gives a
  reason for each difference.
- **What may be written (D6):** untracked or gitignored tooling files, in place, after the plan and a yes, with a
  backup, a receipt and a rollback. Tracked files go through a PR from a scratch clone; the commands refuse tracked
  files and repos mid-merge.

## Docs

- **Filenames are plain names (D8), without dates.**
- **The H1 is a short name for what the doc contains.** The revision goes in badges on the line under it
  (shields.io: `Revision` and `Revised`), never in the title. `AGENTS.md` and `CLAUDE.md` carry none.
- **Revision numbers change only with content.** Moving a file or fixing a link doesn't count.
- **Docs are checked.** `just docs` runs markdownlint (`.markdownlint-cli2.jsonc`) and lychee offline
  (`lychee.toml`) over every Markdown file, and the Docs check workflow runs the same on every PR. `just links` also
  fetches external URLs. A broken link between docs, a bad #fragment or a dead URL fails the run.
- **Where docs live:** living docs (reference, runbooks) in `docs/<area>/`; every doc listed in
  [`README.md`](README.md). Records of what happened on a particular machine belong in that machine's instance.

## Decisions

Newest first. Some record one-off choices; they keep their numbers because code and docs cite them.

| # | Decision | Chosen, and why |
| --- | --- | --- |
| D64 | One contract for package managers (parity 0.2) | **Each package manager and kind of package is a *source*, and the take-or-hold call is made in one place.** A source (`lib/providers/index.js`; Homebrew's two, formulae and casks, are in `lib/providers/brew.js`) names its platforms and families (D63), its gate mode (D-a), the `host.toml` exception kind it honours, whether it needs root, and the way back when its upgrade fails. It also says how to tell it is installed, refresh its metadata, list what is behind, date a version, list what needs a hand, and upgrade a list of packages. `judge()` makes the call for both `steward sc audit` and `steward sc plan`: an unexpired security exception is taken, a version at least the gate's days old is taken, anything younger or undated is held. Before this, the same rule was written twice, in the audit's Homebrew checks and in the plan. The plan loops over the sources that apply here. One that isn't installed says `<manager> not found: skipped`, and isn't refreshed (`steward sc plan` used to call `brew` on a machine without it). The plan is `{packages: [{source, names}], tools, updaters, miseSelf}`, and `apply` runs each source's own upgrade. **A source that needs root is never run:** the plan lists it as `manual`, with its exact `sudo` command, and `apply` refuses it, until the hand-off of D-b arrives with the apt provider (the owner's choice, 2026-11-01). **mise is not a source:** it applies the gate itself and keeps its own path (`upgrade-tool`, `node-patch`, the tools AI tooling owns). The Mac's host report, audit and plan were identical before and after on the owner's Mac (2026-11-01: five formulae held, pandoc taken), once clock stamps and the daily Homebrew download are set aside. **Why:** apt, dnf and zypper each become one source file and its tests, with no edits to the plan or the audit. **Rejected:** building the root hand-off now (it would be designed before a manager that needs it exists to test it on); making mise a source (it would duplicate the gate mise already applies) |
| D63 | Knowing the Linux distribution, and entries for some distributions only (parity 0.1) | **`lib/platform.js` reads os-release and names a family; `host.toml` takes an optional `families` key.** On Linux, `describe()` reads `/etc/os-release`, else `/usr/lib/os-release` (the format's fallback), and gives the distribution (`ID`), its version (`VERSION_ID`) and its family: one of `debian`, `rhel`, `suse`, `arch`, `alpine`, `void`, `gentoo`, `slackware`, `nixos`, found from `ID` first, then each `ID_LIKE` word (Linux Mint and Pop!_OS land in `debian` that way). It is `null` for a distribution it doesn't know, and on macOS and Windows, where nothing is read. The family is what the providers, the trust store and the install hints will go by (`docs/platforms/parity.md`). A `host.toml` entry narrows its Linux part with `families = ["nixos"]`; its macOS part, if it has one, is unchanged. **An entry with `families` must also say `platforms = ["linux"]`**: an older steward ignores `families`, so without it a NixOS-only entry would hold everywhere there. The steward warns when it is missing, and still treats the entry as Linux only. An unknown family name is warned about as an unknown platform is. The audit and plan headers name the distribution on Linux, as `linux (ubuntu 24.04)`. `steward sc host` names it with the family, as `host policy (linux, ubuntu 24.04, family debian)`. macOS output is unchanged: the same host report, and the same audit and plan once clock stamps and caches are set aside (2026-11-01). **Why:** the owner chose `linux` plus `families` over a separate `nixos` platform (D-f, 2026-10-31): one key covers NixOS and the differences between other families, with no format change. The owner chose to require `platforms` beside `families` rather than bump the format (2026-11-01). **Rejected:** `nixos` as its own platform (every Linux default would have to list both); a schema bump (it would pull in `steward migrate`, deferred to the first format change); accepting the risk (a mixed-version machine could apply a NixOS-only entry on macOS) |
| D62 | Three writers that broke the shape | **Each now plans, asks, backs up and writes a receipt with a way back, like the rest.** `steward ai guard` creates a missing `~/.claude/settings.json` (it stopped with `ENOENT` on a fresh Mac), as the git ignore guard creates its file: the receipt records it didn't exist, and `--rollback` removes it. `steward sc install-hybrids` prints its plan (each hybrid, its allowed install scripts, the Ruflo policy backup when Ruflo's version changes) and asks with class `install-hybrids` (it asked nothing); `sc node-patch` is unchanged. `steward projects decide` and `steward projects --apply` back up `registry.toml` to `backups/registry-<time>/` and write a receipt naming each change before → after; `steward projects decide --rollback <receipt>` restores it only if nothing changed it since, and starts no soak. **Why:** the owner chose these on 2026-10-31, after #73 found them: the protection matters most on a fresh Mac, and every writer should have the same plan, yes, backup, receipt and way back. **Rejected:** skipping the guard without a settings file (the npx protection stays off when it matters most); asking only when Ruflo changes (two rules); relying on Git for the registry (an instance that isn't a repo has no way back) |
| D61 | Jobs that take several commands | **Bundled commands: every part's plan, one yes, one record** (`lib/coarse.js`). `steward ai fix` runs `ai repin`, `guard`, `timeouts`, `approvals` and `transport`; `steward fleet tidy <repo>` runs `fleet sync`, then `prune-merged`; `steward projects apply` runs `projects onboard` and `offboard` where the registry's decision and the project differ, then `projects reconcile --all` when copies are behind (a project whose plan refuses is the user's, named, never a part); `steward upgrade` runs `sc node-patch` for a newer security release on the active Node's line (from nodejs.org), else `sc install-hybrids` when the briefing's hybrid check finds them out of step, then `sc upgrade`. Each part's own plan prints first (`DRY_RUN=1`, no `--apply`); the plan names the Node step and the Ruflo policy backup. At a terminal it asks once; each part then runs through this engine's `bin/steward.js` with `--unattended --yes-to <its class>` (D59), so every question a part asks is still checked by its own class (D58). Without a terminal it only plans; with `--unattended`, `[autonomy]` answers and nothing is widened. A bundled command's class is that of its most demanding part (`ai-fix`, `prune-merged`, `onboard`, `upgrade`), for the outer check. The runner is `steward fix`'s (`work()`): a part that stops at a question it may not answer waits on the user (exit 4); a failure stops the rest (exit 1). The record, `backups/coarse-<name>-<time>/receipt.json` (kind `coarse`), names every receipt the parts wrote and starts no soak of its own; the briefing names one left unfinished once its process is gone. To make this work, the five AI fixers, onboard, offboard and `upgrade.js` answer through `A.answer(class, q)`, and `install-hybrids` asks with class `install-hybrids` (D62). `sc node-patch` reinstalls the hybrids under its own class (`node-patch`), as before; its cross-major question has no class, so it never takes a yes unattended. Bare `steward projects --apply` asks each new project's decision, then records them as `projects decide` does. **Why:** the owner chose coarse commands (2026-10-30): one informed yes for the routine, with each part's plan, backup, receipt and way back unchanged. **Rejected:** making the parts aliases of the bundle (`ai repin --apply` would then do all five); piping `y` into each part (one yes would answer questions of other classes); a new channel for the yes (`--yes-to` already carries it, and receipts record it) |
| D60 | How many commands a user sees | **Tiers, groups and old names, in `lib/commands.js`; `steward help` shows eight.** Every command has a `tier` (`everyday`, `advanced` or `internal`) and a `group` (a heading of `steward help --all`). The everyday set is bare `steward` (the briefing), `review`, `fix`, `upgrade`, `config sync`, `projects`, `rollback` and `doctor`. `steward help` shows those with a line on when to use each (or, for one whose add-on is off, how to turn it on), then "N more for specific jobs: `steward help --all`". `--all` groups every command by area, everyday first, each marked read-only or writes, with the old names at the end. Internal ones (`skills path`) appear only with `--internal`, and `steward help <command>` shows one command's usage, class, way back and old names. The top-level `upgrade`, `rollback` and `projects` run `sc upgrade`, `sc rollback` and `projects scan`. `doctor` shows the engine, the config's format and the add-ons before the prerequisites. `sc plan` took over `sc status`'s Node, hybrids and vendored-Node sections. An old name is an `aliasOf` entry: it runs its new form after one line on stderr, and is never removed outside a major release (`lifecycle.md`). This amends D3's "no aliases" for user commands. **Why:** the owner judged 40-odd commands too many to learn (2026-10-30); a few cover the routine, and old names in receipts, scripts and habits keep working. **Rejected:** removing names (it breaks receipts' rollback lines and scripts); a help text kept apart from the list (it drifts) |
| D59 | Turning the work list into done work | **`steward fix`, an engine runner, driven by a skill** (`lib/fix.js`, `skills/fix/`). It works `steward brief --plan` (or a `steward review --json` list, `--from`) top down and runs only `steward` commands, through its own engine's `bin/steward.js` (never the release on PATH), with the instance named. It decides each step from the command and `[autonomy]` itself, never from the list's `actor`: run (read-only or allowed: `--apply --unattended`), ask (wired, needs a yes), terminal (not wired: it asks its own questions), yours (human-only, or not a `steward` command: never run), skill (maintainer flows, qualifications, fleet repos), wait. A step waits on an `after` that didn't get done; exit 4 waits on the user; any other failure stops the run with its rollback. The user's yes in a conversation reaches a command as `--yes-to <class>`: only with `--unattended`, a real class, for one step (`steward fix --only <id>`), recorded in the receipt (`yes_to`). Each run writes `backups/fix-<time>/receipt.json` with its pid and every step's log; the briefing flags one left unfinished unless its process is still running, and a run starts no soak. **Why:** the owner asked that `steward review`'s evidence become done work, with the maintainer's cycles fast and users getting as much done as is safe, without the model improvising shell commands. **Rejected:** the skill running each step's command itself (the policy would rest on the model); piping `y` to a command (one yes would answer every question it asks); pre-approving `steward fix` in the skill (it writes, so Claude Code asks first) |
| D58 | Who takes each step, and what may run unattended | **The engine labels every step; the instance sets how far it goes.** Each finding, work-list item (`steward brief --plan`) and `steward review --json` item carries a `class` (what kind of change, `lib/autonomy.js`) and an `actor`: `agent` (read-only, or a class the policy allows), `agent-with-yes` (an engine command that writes, after the user's yes) or `human` (merges, sudo, trust stores, dashboard ticks, by-hand fixes, any shell command that isn't a `steward` command). `[autonomy] level` is `ask`, `safe` (the default: read-only, `pull`, `reconcile`, `prune`, `qualify`, `pr-prep`, `fleet-sync`) or `maintainer` (adds `prune-merged`, `release-verify`, `repin`); `allow` and `deny` adjust it. A fast-forward after merges is reversible, so users get it; deleting branches unattended is the maintainer's (the owner's choice, 2026-10-31). `--unattended` is checked twice: `bin/steward.js` refuses a command that isn't wired for it or whose class isn't allowed, and each question the command asks is checked again by its own class (config sync's pull, `mise install` and send are `pull`, `install` and `push`). A refusal exits 4 (waiting on the user, not a failure); receipts record `unattended: true`. `STEWARD_UNATTENDED` from the environment is dropped, so only the check sets it. **Why:** the owner wants fast maintainer cycles and users to get as much done as is safe, especially after a `steward review`, without leaving the call to the model. **Rejected:** letting the model judge each step (not reviewable, not testable); one yes for a whole command (config sync would push under a `pull` allowance); a class for human-only steps (a setting could then allow a merge). Fixed whatever the setting: plan, backup and receipt for every write; stop on failure; the release-age gate |
| D57 | What may run without being asked | **Nothing changes on its own; looking is automatic.** Read-only checks may run unprompted: the `steward` banner, `steward brief`, and a **background refresh** of the briefing's cache (`lib/refresh.js`). When that cache (`<state>/brief/refresh.json`) is older than `[brief] refresh_hours` (default 6; 0 turns it off, so nothing touches the network unprompted), `steward brief` starts it after printing and doesn't wait: detached, at low priority, behind a lock (`refresh.lock`; one older than 10 minutes, or whose process is gone, is taken over), at most 120 s in all and each step with its own limit. Its steps only read: a `git fetch` of the config repo (`[brief] fetch`, default true; no prompts: `GIT_TERMINAL_PROMPT=0` and ssh in batch mode), which changes only `FETCH_HEAD` and the remote's branches, never your branch or files; npm's newest `workstation-steward` and its publish time; new and vanished projects (`newAndGone()`); `steward ai drift --offline --json`; `mise current node`. It writes only its cache (temp file and rename, mode 0600; the tools it asks keep their own caches, as whenever you run them); a step that fails or runs out of time is recorded, and the rest still run. It never runs a full reconcile plan (that writes `seen.json`), the gate's queue (that moves the review's anchor), `steward sc audit` or `gh`. `STEWARD_NO_REFRESH` or `CI` keeps it from starting; `steward brief --refresh` runs it in the foreground. **Every write still needs a plan, your yes, a backup and a receipt**, and there are still no cron or launchd jobs. Rejected: launchd or cron (a job that outlives the session, runs when nobody reads its output, and is one more thing to install and remove); fetching inside the Claude Code session hook (it would hold up every session start on the network); fixing what the refresh finds (a write without a plan and a yes) |
| D56 | Seeing what the release-age gate holds back | **Read Renovate's Dependency Dashboard, read-only** (`lib/gatequeue.js`). For the config repo and the fleet's repos the review already reads, it finds the open dashboard issue (`gh issue list --author app/renovate`) and reads the checkbox lines under three headings: Pending Status Checks (held by the gate), Pending Approval (waits for a tick: the AI-owned tools, `dependencyDashboardApproval` in `renovate/steward.json`) and Awaiting Schedule (the weekly "mise tools" digest). For each version it looks up the publish time (npm's time map; the GitHub release for an action, `jdx/mise` or Node), adds `[policy] min_release_age_days`, and names the next step: wait until a time, Renovate opens the PR, qualify then tick, review then tick, or wait for the schedule; a 0.x update adds "read its changes", Node adds `steward sc node-patch`. A version given as "latest", or a name npm doesn't have at that version, says "Renovate times it". **`steward review` lists them** as "Waiting on the release-age gate", cleared first, then by clear time; `--quick` skips it, like the audit. It writes `<state>/review/gate-queue.json`, and **the `steward` banner reads only that file** (no network) to say how many cleared since the review. Nothing is ticked: a tick under Pending Status Checks opens the PR before the gate clears. Rejected: a hand-kept list of what's queued (every item typed in, and it misses whatever Renovate adds next); Renovate's or Mend's API (a token to store; the issue is what the owner's `gh` login already reads); the banner asking GitHub (every `steward` run would touch the network) |
| D55 | A per-project-only tool switched on at user level | **Its profile says what stays off, and drift checks it.** A profile's `[user_off]` table names the user-level Claude plugins (`~/.claude/settings.json` `enabledPlugins`), Codex plugins (`~/.codex/config.toml` `[plugins."…"]`) and Codex MCP servers (`[mcp_servers.…]`) that must stay off; `steward ai drift` reports each one that is on as DRIFT, with the fix (set it to false, or remove the block), and never changes it. Brain lists all three (D18: on per project only; its installer writes the Codex server block on every run, which loaded its tools in every Codex session on 2026-10-29). Ruflo lists its three Claude plugins, which its profile already called project-scoped. Every shipped profile with the table is checked, whether or not a project chose the tool: the rule holds either way. Onboarding never reads the table. Rejected: user-level kinds in `[[keep_off]]`, which lives in each instance and covers project files (every user would have to add the entries; this ships with a release) |
